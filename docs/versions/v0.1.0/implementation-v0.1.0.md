## 1. 实施目标与约束

本文只说明如何实现 `docs/versions/v0.1.0/prd-v0.1.0.md` 已确认的产品要求，不重新定义产品范围。开发过程中遇到产品行为冲突时，以 PRD 为准；遇到字段结构冲突时，以 JSON Schema 为准，并同步修正文档引用，不能在代码中建立隐式的第二套格式。

V1 的实施需要同时交付 AI Agent Skill 和本地显示工具。两者必须通过 `.chordsheet` 解耦，不能共享运行时内存、私有数据库结构或模型专属输出。显示工具的导入、阅读、编辑、转调、保存和导出在没有 AI API 的情况下可用。

以下限制贯穿全部实现：

1. 不建立后端、账号、云端同步或 API Key 设置；
2. 不在显示工具中加入原始材料识别流程；
3. 不实现节奏数据的页面显示，但必须无损保存合法节奏字段；
4. 不推算推荐 Capo；
5. 不生成或展示无法追溯的和弦指法；
6. 不用像素坐标代替歌词字素锚点。

## 2. 技术架构

### 2.1 总体数据流

系统按以下顺序流转：

```text
复制文字 / 截图 / PDF
          ↓
通用 Agent 核心规则 → Codex Skill 适配
          ↓
结构化文档 → Schema 校验 → 语义校验 → ZIP 打包
          ↓
                    .chordsheet
                          ↓
归档安全检查 → 解压 → Schema 校验 → 语义校验
                          ↓
                    本地曲库
                          ↓
阅读 / 编辑 / 转调 / Capo / 指法 / PDF 与谱包导出
```

Schema 校验只负责字段类型、枚举和基本范围。ID 唯一性、引用存在性、锚点边界、归档路径和指法数组长度等跨字段规则由共享语义校验器负责。Agent 打包和工具导入必须调用同一套校验规则，避免“Agent 认为有效、工具却无法导入”。

### 2.2 技术选型

显示工具采用 React、TypeScript 和 Vite 构建静态响应式 Web 应用。样式使用项目内 CSS，不引入通用组件库，以便精确控制纸质谱式排版并减少无关视觉风格。V1 不把 PWA 安装、部署平台或 Service Worker 作为验收条件。

实际采用的基础依赖如下。版本由 `package-lock.json` 冻结；`package.json` 保留兼容范围，后续升级必须重新运行构建、单元测试和端到端测试。

| 能力 | 计划实现 |
|---|---|
| Schema 校验 | Ajv 与 Ajv Formats，使用 JSON Schema 2020-12 |
| ZIP 导入导出 | fflate |
| 本地曲库 | IndexedDB；用 Dexie 隔离浏览器事务细节 |
| 单元与组件测试 | Vitest 与 Testing Library |
| 浏览器端到端测试 | Playwright |
| 字素分段 | 浏览器 `Intl.Segmenter`，按 `grapheme` 粒度 |
| PDF | 浏览器打印能力与专用打印 CSS |
| 指法图 | 由已核验数据驱动的内联 SVG |

React 状态仅负责当前页面交互；持久数据通过独立 repository 接口读写 IndexedDB。转调、锚点、校验和谱包处理保持为无界面的纯模块，便于 Agent 脚本、页面和测试复用。

选型依据来自各项目的一手文档：[Vite React 与 TypeScript 模板](https://vite.dev/guide/)、[Ajv Draft 2020-12](https://ajv.js.org/json-schema.html)、[Ajv Formats](https://ajv.js.org/guide/formats)、[Dexie React 指南](https://dexie.org/docs/Tutorial/React)、[fflate ZIP 实现](https://github.com/101arrowz/fflate)和 [Playwright 浏览器与移动设备配置](https://playwright.dev/docs/browsers)。依赖安装后仍需以锁文件和实际测试结果为准。

## 3. `.chordsheet` 归档实现

### 3.1 归档结构

`.chordsheet` 使用 ZIP 容器，不加密。归档根目录必须包含且只包含一个 `chordsheet.json`；原始材料存在时放在 `sources/` 下。其他根目录文件在 V1 中拒绝导入，避免未定义内容形成兼容负担。

```text
song.chordsheet
├── chordsheet.json
└── sources/                 # 可选
    ├── copied-text.txt
    ├── page-1.png
    └── original.pdf
```

`chordsheet.json` 使用 UTF-8，不带字节顺序标记。ZIP 内路径统一使用 `/`，区分大小写，不允许绝对路径、反斜杠、空路径、`.`、`..`、符号链接或指向归档外部的路径。

### 3.2 导入安全限制

V1 在读取文件内容前检查 ZIP 中央目录，并执行以下明确限制。条目没有可用的未压缩大小时直接拒绝，不能先完整解压再判断是否超限。

| 限制 | 数值或行为 |
|---|---|
| 压缩包大小 | 不超过 100 MiB |
| 文件条目数 | 不超过 100 个 |
| 总解压大小 | 不超过 300 MiB |
| `chordsheet.json` | 不超过 5 MiB |
| 单个来源文件 | 不超过 100 MiB |
| 加密条目 | 拒绝 |
| 重复路径 | 拒绝 |
| 路径穿越与符号链接 | 拒绝 |

这些限制只保护本地浏览器免受异常归档占用内存或覆盖路径，不限制结构化谱面的歌曲长度。超过限制时工具拒绝导入并保留原曲库不变。

### 3.3 校验层级

导入和打包按固定顺序校验：

1. 检查 ZIP 类型、归档路径和大小限制；
2. 读取并解析 `chordsheet.json`；
3. 根据 `formatVersion` 选择对应 Schema；
4. 执行 JSON Schema 校验；
5. 执行跨字段语义校验；
6. 检查声明为已嵌入的来源文件存在且路径一致；
7. 只有全部通过后才写入本地曲库或交付谱包。

V1 只支持 `formatVersion: 1.0.0`，不实现虚假的旧版本迁移。导入器保留按版本分派的边界，未来增加版本时必须新增明确迁移和合同测试。

### 3.4 语义校验规则

共享语义校验器至少执行以下规则：

1. 来源、段落、行、和弦、指法和节奏型的 `id` 在整个文档内全局唯一；`documentId` 只标识谱包本身，不参与对象引用；
2. `sourceId`、`voicingId` 和 `rhythmPatternId` 引用真实存在且类型正确的对象；
3. 歌词和弦的 `graphemeOffset` 不超过对应歌词的字素数量，同一歌词行不出现重复锚点；
4. 同一歌词行的和弦事件按 `graphemeOffset` 升序保存；
5. `embedded: true` 的来源有合法路径和真实归档条目，`embedded: false` 的来源没有归档路径；来源包含 `sha256` 时，解压后的文件摘要必须一致；
6. 指法的 `tuning`、`frets` 和可选 `fingers` 数组长度一致，横按弦号和品位处于有效范围；
7. 指法 `verification.status` 必须为 `verified`，并存在核验方法和引用；
8. 节奏事件的 `slot` 小于所属节奏型的 `stepsPerMeasure`，同一节奏型不包含重复 `slot`，段落引用的节奏型存在；
9. `baseWrittenKey` 存在时能被调性模块解析；不存在时实际调保持未知；
10. 来源的归一化区域满足 `x + width <= 1` 和 `y + height <= 1`。

Schema 允许保存暂时无法转调的和弦文本，因为原始符号不能因解析器能力不足而丢失。此类符号不导致导入失败，但转调操作必须保持原样并向用户说明。

### 3.5 错误模型

导入器使用稳定错误码和可定位路径，页面负责把技术信息转换为简洁提示。V1 至少区分：

| 错误码 | 含义 |
|---|---|
| `PACKAGE_INVALID_ZIP` | 文件不是可读取的 ZIP |
| `PACKAGE_LIMIT_EXCEEDED` | 文件数、压缩或解压大小超过限制 |
| `PACKAGE_UNSAFE_PATH` | 存在非法路径、重复路径或符号链接 |
| `DOCUMENT_MISSING` | 缺少根目录 `chordsheet.json` |
| `DOCUMENT_INVALID_JSON` | 根数据不是有效 UTF-8 JSON |
| `VERSION_UNSUPPORTED` | 格式版本不是 `1.0.0` |
| `SCHEMA_INVALID` | 字段结构违反 Schema |
| `SEMANTIC_INVALID` | ID、引用、锚点或跨字段关系无效 |
| `SOURCE_MISSING` | 已声明嵌入的原始文件不存在 |

失败结果包含错误码、可用的 JSON Pointer 或归档路径和一条用户可理解的说明。任何导入失败都在写入 IndexedDB 之前结束。

## 4. 领域数据与核心算法

### 4.1 字素锚点

运行时使用 `Intl.Segmenter("und", { granularity: "grapheme" })` 把歌词分成 Unicode 字素。`graphemeOffset: 0` 表示歌词第一个字素之前；偏移等于字素总数时表示歌词末尾边界。Agent 和显示工具必须按同一定义计数，不能使用 JavaScript 字符串长度、UTF-16 码元或视觉列数代替。

渲染器先把歌词和和弦转换为按锚点切分的逻辑片段，再由 CSS 负责换行。和弦与其后的歌词片段属于同一不可拆语义单元；片段过长时只允许歌词内部换行，和弦不能独自留在前一视觉行。

### 4.2 歌词编辑时的锚点变换

编辑器用一次文本变更的旧范围、新文本和字素差值更新锚点：

1. 变更范围之前的锚点保持不动；
2. 变更范围之后的锚点按字素差值平移；
3. 落在被替换或删除范围内的锚点移动到变更起点；
4. 第三类锚点的复核状态改为 `unreviewed`、置信度改为 `low`，原因记为 `positionConflict`；
5. 用户拖动锚点后，状态改为 `corrected`。

编辑界面使用受控文本输入和独立的和弦锚点轨道，不使用一个同时承载文本、拖动对象和排版的 `contenteditable` 区域。这样可以让字素差值和选择状态保持可预测。

### 4.3 转调

谱包中的 `symbol` 保存修正后的基础和弦，页面根据 `view.transposeSemitones` 计算显示和弦，不把计算结果写回基础值。恢复原调只需把半音偏移设为 0，因此不会经历多次转调累积或异名音丢失。

解析器只改写音高名称，不解释或重写和弦性质：

1. 从开头读取 A 到 G 的根音及可选 `#`、`b`、`♯`、`♭`；
2. 只有末尾符合 `/音名` 的部分才视为 Slash bass，`C6/9` 中的 `/9` 保留在后缀中；
3. 根音与 Slash bass 分别转换为音级并移动相同半音数；
4. 中间后缀逐字符保留，包括 `m`、`maj7`、`sus2`、括号和扩展音；
5. 无法安全解析的符号保持原样，当前操作结果显示“不支持转调”，不能部分改写。

用户选择目标调时，以目标调决定升降号偏好；按半音按钮时，沿用当前书面调的调号体系。顶部概览、正文和指法查询都消费同一份计算后的和弦结果。

`metadata.baseWrittenKey` 缺失时不提供目标调选择，因为无法把目标调可靠换算为半音偏移；半音升降仍可直接作用于可解析的和弦。编辑模式始终读取和修改基础 `symbol`，暂时隐藏但不清除当前转调偏移，返回阅读模式后再应用偏移。

### 4.4 Capo 与实际发声调

`view.capo` 是独立的手动阅读设置。当前书面调等于 `metadata.baseWrittenKey` 加 `view.transposeSemitones`；实际发声调再上移 `view.capo` 个半音。任何一步缺少可解析书面调时，页面显示“实际调未知”。改变 Capo 不修改和弦符号、锚点或转调偏移。

Agent 解析来源元数据时先判断 `Key` 表示书面调还是实际发声调。来源同时给出实际调和 Capo 时，基础书面调等于实际调下移 Capo 半音数；The Cure 基准应得到 `baseWrittenKey: C` 和 `view.capo: 1`。该计算与正文和弦明显冲突时不写入 `baseWrittenKey`，并把冲突纳入交付摘要。

### 4.5 指法选择与渲染

指法查询按当前显示和弦、完整调弦和精确符号匹配，优先级如下：

1. 谱包内与当前和弦及调弦完全匹配、并带有有效核验记录的指法；
2. 应用内已完成许可审查和人工抽检的本地指法库；
3. 没有可靠结果时返回“暂无指法”。

系统不能根据另一个和弦图自动移动品位生成未知指法，也不能把原调的嵌入指法直接用于转调后的不同和弦。内置库使用 `@tombatossals/chords-db` v0.6.0 的 MIT 许可数据，经紧凑转换后保留 828 个和弦条目和 3,283 个按法；来源、许可证与转换范围记录在 `THIRD_PARTY_NOTICES.md`。其原始相对品位在加载时转换为 SVG 所需的绝对品位，横按范围由同一品位的弦位推导；许可无法确认的数据不进入仓库。

SVG 渲染器只消费结构化的闷弦、空弦、绝对品位、手指和横按数据。相同指法只渲染一份可复用定义；页面实例提供包含和弦名称与品位信息的无障碍标签。

## 5. AI Agent 与 Codex Skill

### 5.1 Skill 边界

`skills/chordsheet/` 是可分发的 Codex Skill。开发时必须使用 Codex 的 skill-creator 工作流建立合法结构。Skill 只负责从材料到谱包，不包含显示工具代码，也不要求访问本地曲库。当前可安装 ZIP 由该目录直接打包，静态交付物位于 `public/downloads/chordsheet-builder-skill-v0.1.0.zip`，解压根目录为 `chordsheet/`。

平台无关的核心规则放在 Skill 的 `references/`，包括来源优先级、字素锚点、复核状态和打包验收。`SKILL.md` 只负责任务路由和执行步骤，避免把完整规则复制到入口文件。ChatGPT 交付物由同一核心内容生成，不另写一套字段解释。

### 5.2 Agent 执行阶段

一次制谱任务按以下阶段执行：

1. 列出收到的材料，并询问是否嵌入原始材料；
2. 解析必需元数据；标题或调弦缺失时向用户确认，不能自行补成确定值；
3. 对 PDF 先渲染页面，再结合截图判断视觉位置；
4. 建立规范化歌词、段落和基础和弦；
5. 把每个歌词和弦转换为字素偏移，并记录可选证据；
6. 对冲突和推断项目写入复核状态；
7. 只在来源明确时加入节奏和指法，缺失时省略；
8. 运行 Schema 和语义校验；
9. 按用户选择复制来源文件并生成 ZIP；
10. 重新打开成品完成一次导入级校验；
11. 交付谱包，并报告低置信数量、是否嵌入来源和校验结果。

如果当前 Agent 环境不能运行校验或生成 ZIP，只能交付标明“未完成打包”的结构化草稿，不能把 JSON 文本改名为 `.chordsheet` 后声称成功。

### 5.3 来源处理

Agent 将复制文字视为内容证据，将截图视为位置证据；没有截图时，PDF 渲染图承担位置证据。视觉材料与复制文字冲突时，Agent 分别解决“内容是什么”和“位置在哪里”，不能用一份来源粗暴覆盖全部字段。

PDF 页码和归一化区域可以作为和弦证据写入谱包。显示工具不依赖这些坐标渲染，但编辑模式可以据此说明低置信结果来自哪份材料。V1 不实现原始材料并排校对页面，因此证据只保存在数据中。

## 6. 本地显示工具

### 6.1 本地曲库

IndexedDB 使用 `documentId` 作为歌曲主键，并保存结构化文档、来源 Blob、标题、歌手和更新时间索引。页面通过 repository 接口执行导入、读取、保存、删除和替换，不直接在 React 组件中调用 IndexedDB。

IndexedDB 数据绑定当前浏览器来源。正式构建需要从稳定来源提供，不能把开发端口或临时预览地址当作长期曲库入口。静态托管只分发应用文件，不提供后端数据服务；用户换来源、换浏览器或清除站点数据时，通过手动导出的 `.chordsheet` 恢复歌曲。

导入相同 `documentId` 时先在内存完成全部校验，再显示替换确认。用户确认后使用单个事务替换结构化文档和来源 Blob；事务失败时保留旧版本。删除也使用单个事务，并在执行前由页面确认。

编辑后的自动保存采用最后一次变更后 500 ms 合并写入，并在切换歌曲、退出编辑和导出前强制刷新。repository 返回明确的保存状态；失败时页面保持脏状态并持续显示错误，不能更新为“已保存”。

### 6.2 页面状态

应用只有两个主要页面：本地曲库和歌曲页面。歌曲页面内部区分阅读与编辑状态，不为每种工具建立独立路由。

阅读状态根据当前文档派生显示和弦、实际调和和弦概览。点击正文和弦或工具栏指法按钮更新全局 `chordDisplay`。编辑状态复用同一份领域文档，但用行编辑器和锚点轨道替换只读谱面；点击和弦只选择事件，不触发全谱指法切换。

手机断点不改变数据模型。手机保留转调、Capo、字号和全谱指法控制，隐藏完整编辑入口并明确提示到桌面端校正；桌面端编辑产生的谱包在手机导入后仍能完整显示。

### 6.3 PDF 导出

PDF 使用独立打印样式而不是截图整页。打印前从当前阅读状态生成只读 DOM，并隐藏工具栏、低置信标记、编辑控件和来源证据。CSS 使用 `break-inside` 和段落标题的分页约束，保持和弦与歌词片段、标题与首行在同一页。

浏览器打印对话框是 V1 的 PDF 生成入口，不加入服务器端或大型 PDF 生成依赖。端到端测试检查打印 DOM 的内容状态；最终 PDF 分页和字体需要人工渲染检查。

### 6.4 无障碍与输入方式

所有工具栏操作使用原生按钮语义并提供可见焦点。转调、Capo、字号和指法切换可通过键盘操作；拖动锚点同时提供“向前一个字素”和“向后一个字素”的键盘操作。低置信标记不能只依赖颜色表达。默认控件在按下时提供短促缩放反馈；`prefers-reduced-motion` 取消该位移动画，`prefers-reduced-transparency` 和 `prefers-contrast` 分别提升表面不透明度与边界对比度。

## 7. 导出实现

### 7.1 `.chordsheet` 导出

导出器从本地曲库读取最新文档和来源 Blob，先刷新自动保存，再执行语义校验。用户选择移除来源时，导出器删除 `sources/` 文件，把对应来源记录的 `embedded` 改为 `false`，并移除 `path` 与文件哈希；来源类型、角色和原始文件名可以保留。

归档使用确定性文件顺序和稳定 JSON 缩进，方便测试和差异检查。时间字段只在真实内容或阅读设置改变时更新，不能因重复导出产生无意义修改。

### 7.2 往返一致性

自动化测试执行“导入 → 保存 → 导出 → 重新导入”。除 ZIP 压缩元数据外，第二次导入得到的结构化文档、来源字节和复核状态必须与导出前一致。选择移除来源是唯一允许主动删除来源字节的导出路径。

## 8. 测试策略

### 8.1 合同与单元测试

合同测试以 `schema/chordsheet.schema.json` 和 `examples/anchor-check/chordsheet` 为起点，覆盖有效包、缺失根文件、非法路径、重复 ID、越界锚点、缺失来源、无效指法及节奏引用。Schema 文件本身需要通过 JSON Schema 2020-12 的 meta-schema 检查。

领域单元测试至少覆盖：

1. 英文、中文、组合音标和 emoji 的字素计数；
2. 歌词插入、替换和删除后的三类锚点变换；
3. `C`、`Bbmaj7`、`F#m7`、`G/B`、`C6/9` 和无法解析符号的转调行为；
4. 恢复原调后基础和弦逐字符不变；
5. Capo 与实际发声调计算；
6. 指法优先级、调弦匹配和缺失回退；
7. 导出移除来源后的记录一致性。

### 8.2 组件与端到端测试

组件测试覆盖曲库空状态、导入结果、替换确认、保存失败、低置信状态、全谱指法切换和编辑状态冲突。端到端测试至少运行一个桌面视口和一个手机视口，完成导入、阅读设置、桌面编辑、自动保存、导出及重新导入。

响应式验收不能只比较截图。测试需要读取和弦事件对应的歌词片段，确认换行前后仍属于同一逻辑锚点；视觉截图用于补充检查字体、间距、溢出和分页。

### 8.3 The Cure 人工验收

用户提供的 `The Cure Chords by Olivia Rodrigotabs @ Ultimate Guitar Archive.pdf` 不复制进仓库。发布候选版本使用该三页 PDF 完成以下人工验收：

1. Agent 生成候选谱包并列出所有低置信位置；
2. 逐段核对歌词、段落、和弦名称和字素锚点；
3. 修正后确认全部可见和弦达到 100% 正确；
4. 逐一核验 Asus2、Cmaj7、Fmaj7、Dm、F、C、G/B、G 指法；
5. 在桌面和手机检查换行、转调和全谱指法模式；
6. 导出当前状态 PDF，重新渲染所有页面，检查无裁切、重叠、孤立段落标题或和弦歌词分离；
7. 导出 `.chordsheet` 并重新导入，确认结果一致。

## 9. 开发阶段与完成标志

### 9.1 阶段一：合同与纯领域逻辑

实现 Schema 校验、语义校验、ZIP 安全检查、字素锚点、转调、Capo 和指法数据类型。完成标志是合同与领域单元测试全部通过，`anchor-check.chordsheet` 可以完成往返导入。

### 9.2 阶段二：AI Agent Skill

使用 skill-creator 建立 Skill，写入来源处理、PDF 视觉判断、复核和打包流程，并调用阶段一的校验脚本。完成标志是纯文字、纯视觉材料和组合材料都能生成可导入谱包，且不能把未校验结果标记为成功。

### 9.3 阶段三：曲库与只读谱面

实现本地曲库、导入、自动保存基础、歌曲页、响应式锚点渲染、转调、Capo 和字号。完成标志是桌面与手机端可以稳定阅读 `anchor-check.chordsheet`，改变宽度后锚点不分离。

### 9.4 阶段四：编辑与指法

实现桌面行编辑器、锚点轨道、复核队列、全谱指法切换和已核验指法查找。完成标志是编辑导致的锚点变化符合规则，手机不暴露完整编辑入口，未知指法不生成图形。

### 9.5 阶段五：导出与端到端验收

实现 `.chordsheet` 往返导出、来源移除和打印样式，完成自动化测试与 The Cure 人工验收。全部 PRD 验收项通过后才能把 V1 标记为完成；测试失败或仍有错误锚点时不能用“已知问题”替代修复。

## 10. 风险控制与开发门槛

| 风险 | 实施控制 |
|---|---|
| 字素定义在 Agent 与浏览器间不一致 | 共享固定测试字符串和预期偏移，打包前执行语义校验 |
| ZIP 在浏览器内造成内存压力 | 导入前检查中央目录、文件数和解压上限 |
| React 排版层与领域锚点耦合 | 先生成逻辑片段，UI 只负责显示和换行 |
| 转调误改复杂后缀 | 只转换根音和确认的末尾 Slash bass，后缀原样保留 |
| 指法库数据不可靠 | 数据进入仓库前完成许可记录与人工抽检，运行时只接受 `verified` |
| Skill 与根 Schema 分叉 | 从根 Schema 生成 Skill 副本并做字节一致性测试 |
| 自动保存产生数据丢失 | 事务写入、脏状态、失败提示和离开前强制刷新 |
| PDF 浏览器差异 | 打印 DOM 自动检查加正式 PDF 的逐页渲染人工检查 |

开始产品代码之前必须满足三个门槛：本文件与 PRD 经用户批准；Schema 和样例通过可用的结构检查并在开发环境接入正式 Schema 校验器；用户明确说“开始开发”。未满足时只能修改规范和文档，不能安装依赖或创建产品代码。

## 11. 实际实施结果与维护状态

本节记录已落库的技术事实，不改变前文的产品要求。完整交付、测试结果、未上线事实和产品差异见 `docs/versions/v0.1.0/release-v0.1.0.md`；PRD 是否已满足仍由 Simon 验收决定。

### 11.1 已落库的模块

1. `src/domain/` 提供字素分段、歌词编辑后的锚点变换、和弦与调性转调、Schema 校验、跨字段语义校验与来源指法优先的内置库解析；`src/package/` 在解压前检查 ZIP 中央目录、路径、大小、加密和符号链接，再完成导入与打包。
2. `src/storage/library.ts` 使用 Dexie 将文档和嵌入来源字节存入 IndexedDB；`src/ui/` 提供曲库、主页 `.chordsheet` 拖放入口、阅读页、编辑器、SVG 指法图和打印样式。`src/styles.css` 用一张实心谱纸承载阅读内容，以轻量材质区分工具层，并包含即时按压、键盘焦点与减少动态/透明度/提高对比度的样式降级。自动保存使用 500 ms 防抖，并在文档未通过当前校验时显示待修正状态而不写入曲库。
3. `skills/chordsheet/` 由 skill-creator 初始化，入口规则与 `references/conversion-rules.md` 共同约束多材料来源优先级、复核、指法追溯与打包；`scripts/sync-skill-schema.mjs` 同步权威 Schema。`public/downloads/chordsheet-builder-skill-v0.1.0.zip` 是其当前可下载包，首页链接以浏览器下载属性指向该文件。
4. `examples/the-cure-reference.chordsheet` 只保存由用户提供 PDF 第 1 页逐一核验的八张和弦图、C 书面调与 Capo 1；它不含原 PDF，也不声称覆盖三页完整歌词和锚点。

### 11.2 已执行的验证

截至本次记录，`npm run test:run` 通过 20 项领域、归档、组件与 The Cure 参考测试，其中包含首页 Skill 下载链接；`npm run build` 成功生成静态构建；`npm run test:e2e` 在本机 Chrome 执行主页真实拖放、桌面阅读/编辑、手机完整阅读控制与桌面编辑提示、The Cure 导入验证。Skill ZIP 已检查包含入口、规则、元数据与 Schema。`npm run validate:example`、The Cure 参考包校验、Skill 快速结构校验和根 Schema 与 Skill Schema 的字节比较均已通过。

端到端配置为同一测试文件运行桌面与手机项目；与当前项目无关的组合会显式跳过，因此最近一次结果为 4 个通过、4 个跳过，而不是失败或遗漏。

### 11.3 已知实现差异与维护边界

当前代码未实现完整多模态识别服务，而是交付让 Codex Agent 执行该工作流的 Skill；未连接外部 API。编辑、来源导出选择、编辑模式点击行为和真实 PDF 分页验收的差异已在 PRD 第 14 节与 Release 中逐项记录。后续补齐任一差异时，应先更新本节涉及的模块事实和测试清单，再将对应 Release 状态交回 Simon 验收。
