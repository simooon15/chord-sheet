## 1. 文档用途与版本定位

v0.1.1 的产品、呈现和数据基线继续有效。本文增加三项范围：

1. 让用户查看同一和弦的多个已核验指法，选择本曲使用的指法，并在本地保存与谱包导入导出之间保持该选择；
2. 将当前谱面转换为有谱么编辑器能够识别的剪贴板内容，使用户复制后可以直接粘贴，并还原段落、歌词行、和弦名称与字符级落点；
3. 将制谱 Skill 的视觉锚定规则收紧为“和弦根音字母对应来源中的精确歌词字素”，消除词首吸附与字符级规则之间的冲突，并把已修正的 Notion 谱包纳入本版本验收记录。

本版本新增用户可见能力，且需要修改指法解析和歌曲编辑行为，因此由 v0.1.1 升为功能版本 v0.2.0。首版优先复用现有数据契约中的 `voicings` 与和弦事件 `voicingId`，不因本功能主动升级 `.chordsheet` 的 `formatVersion`。

## 2. 背景与要解决的问题

### 2.1 现有指法库已经包含多个按法

当前 `src/data/guitar-voicings.json` 来自 `@tombatossals/chords-db` v0.6.0，包含：

- 828 个标准定弦吉他和弦条目；
- 3,283 个指法位置；
- 每个条目至少 2 个指法，最多 7 个；
- C 大调已有 4 个指法。

`src/domain/voicings.ts` 过去会把排序后的全部候选交给调用方，但 `resolveVoicing` 固定取第一个；`Score.tsx` 与 `App.tsx` 也只消费这一结果。因此用户看到的是单一默认指法，而不是数据缺失。库中 774 个条目原本正好有 4 个位置，另有 16 个条目有 5–7 个变体；直接展示全部变体会把较高把位或小众形状与常用形状混在一起。

### 2.2 用户当前无法选择习惯的按法

低把位、开放弦、横按、高把位和省略弦等指法各有音色与难度差异。当前默认排序只偏向低把位与小跨度，可能仍把横按或用户不熟悉的按法排在第一。用户不能查看其余候选、不能主动替换，也无法让选择随歌曲保存。

### 2.3 制谱规则曾存在词首与字符级冲突

制谱 Skill 已要求把 PDF、截图或保留列布局文本中的和弦根音字母映射到歌词具体字素，但旧版 `conversion-rules.md` 同时存在“和弦在单词上方就对齐单词开头”的表述。该表述会把词内和弦错误吸附到词首，与后续字符级规则冲突。

`notion-the-rare-occasions` 的旧生成结果暴露了该问题：

- A 曾锚定在 `ascending` 开头（43），来源实际对齐 `rise` 的 `r`（53）；
- Faug 曾锚定在 `rise` 的 `r`（53），来源实际对齐 `rise` 的 `s`（55）。

运行时渲染器严格按 `graphemeOffset` 插入和弦，不会自行吸附到词首，所以错误数据会被忠实呈现。当前校验器只能检查锚点边界、顺序和引用，不能仅凭 JSON 判断其是否忠于 PDF 视觉位置。

### 2.4 已整理的谱面不能直接进入有谱么

用户经常在有谱么编辑器中继续编辑和发布曲谱。当前 ChordSheet 只能导出 `.chordsheet`、打印或生成 PDF；用户若要把同一内容放进有谱么，需要重新建立段落、粘贴歌词并逐个放置和弦，已经完成的字符级锚定无法复用。

用户提供的复制样本包含固定哨兵和结构化节点，ChordSheet 的段落、歌词、和弦名称与 `graphemeOffset` 均有直接对应关系，因此可以生成兼容内容。这不是公开协议，能否完整还原必须以真实有谱么编辑器的粘贴结果为准。

## 3. 产品目标

1. 用户能发现同一和弦存在多个已核验指法；
2. 用户能通过鼠标、触屏和键盘查看并选择候选指法；
3. 选择默认作用于本曲全部同名和弦，避免逐个重复修改；
4. 用户选择能随本地自动保存、`.chordsheet` 导出和重新导入保留；
5. 转调后不能把原和弦指法错误套用到新的显示和弦；
6. 内置指法继续保持离线、可追溯、许可明确和结构可验证；
7. 制谱 Skill 对 PDF、截图和保留列布局文本统一执行字符对字符锚定；
8. 已修正的 Notion 谱包成为本版本字符级锚定验收样例；
9. 用户能一键复制有谱么兼容内容，并直接粘贴到有谱么编辑器；
10. 粘贴结果完整保留段落顺序、逻辑换行、歌词文本、和弦名称及和弦对应的精确字符。

## 4. 明确不做

1. 不支持只修改某一次同名和弦；
2. 不提供用户手动画或录入全新指法的编辑器；
3. 不根据前后和弦自动推荐最顺手的指法；
4. 不新增音频试听、指法动画或课程讲解；
5. 不在本版本扩展非标准定弦的内置指法库；
6. 不抓取商业吉他网站或导入许可证不明确的数据；
7. 不让校验器声称已自动完成 PDF 视觉一致性判断；
8. 不把没有使用频次数据的结果说成“全网最常用”；界面中的“常用候选”指低把位的常见形状，ChordPro 同形记录只用于低把位候选的并列排序；
9. 不在本版本导入或解析任意有谱么曲谱；
10. 不自动登录有谱么、代替用户上传或发布曲谱；
11. 不宣称能通过剪贴板传递样本协议未包含的标题、歌手、Capo、节奏型、来源记录或自选指法。

## 5. 多指法选择规则

### 5.1 候选来源与优先级

指法选择器只显示 `verification.status: "verified"` 的指法，候选按以下来源合并：

1. 当前用户已经为该和弦选中的指法；
2. 当前歌曲谱包内与显示和弦、完整定弦相符的来源指法；
3. 应用内置指法库中与显示和弦、完整定弦相符、按第 5.4 节筛出的最多 4 个常用候选；
4. 后续通过本版本数据审计流程补入的已核验指法。

相同定弦、闷弦、品位和横按结构的候选只显示一次。去重后总数最多为 4；当前用户已选指法始终保留在第一位，谱包来源指法随后占位，再以常用内置候选补足。来源指法必须保留“原谱指法”身份；内置和补充数据继续保留数据集名称、版本和许可证。

### 5.2 入口与可发现性

右键只能作为桌面快捷入口，不能成为唯一入口：

1. 点击或轻触和弦概览中的指法图，打开“选择〔和弦名〕的指法”；
2. 正文已展开指法图时，点击或轻触该图打开同一选择器；
3. 鼠标悬停或键盘聚焦时显示“换指法”提示；
4. 桌面右键菜单提供“更换指法”；
5. 全谱展开/收起仍由现有明确按钮负责，不能再依赖点击任意和弦图切换全谱状态。

桌面使用靠近触发位置的浮层；窄屏使用底部抽屉。两者承载同一内容和操作语义。

### 5.3 选择器内容

选择器至少显示：

- 当前显示和弦名称；
- 候选总数和当前位置，例如 `2 / 4`；
- 每个候选的完整指法图；
- 客观特征标签，例如“开放弦”“横按”“第 5 把位”“跨度 3 品”；
- 当前选中状态；
- “使用此指法”和“恢复默认指法”操作；
- 没有第二个候选时的说明，不显示无意义的切换控件。

### 5.4 常用四个的排序与限额

`@tombatossals/chords-db` 只将每个 `position` 定义为一个指法变体，并不提供使用频次；因此本版本不声称统计意义上的“最常用”。`src/data/chordpro-common-voicing-order.json` 记录 ChordPro 6.101 (`R6.101.0` 的固定 commit) 中与现有库完全同形的 240 个和弦键及其位置索引，用作可追溯的标准形状依据。

没有用户选择或谱包来源指法时，先排除起始把位高于第 5 把的内置位置；剩余候选去重后最多保留 4 个，不用第 7、12 把等高把位形状凑数。某个和弦在第 5 把以内不足 4 个时，界面可以少于 4 个。

低把位候选按以下稳定顺序排序：

1. 较低的起始把位优先；
2. 有开放弦优先；
3. 无横按优先于横按；
4. 较小的按弦跨度、较少的闷弦优先；
5. 与 ChordPro 标准形状精确相同的候选仅在前述条件并列时优先；
6. 其余相同时保持主库原始顺序。

界面称其为“低把位常用候选”，不暗示网络使用量或唯一正确按法。用户的当前选择即使不在这四个中也必须保留，以免已保存的谱包失去可恢复的选择。

### 5.5 选择作用域

本版本只提供一个清晰作用域：**应用到本曲全部同名和弦**。

“同名”按基础谱中保存的原始 `symbol` 精确匹配。C 与 C/G、C# 与 Db 不自动视为同一组。选择操作更新本曲所有匹配事件的 `voicingId`。

本版本不提供“仅此处”开关，也不在每次选择时弹出作用域确认。

### 5.6 转调行为

指法必须与当前显示和弦及完整定弦匹配：

1. 原调选择 C 指法后，转调为 C# 时不能继续显示该 C 指法；
2. 目标和弦没有保存选择时，回退到该目标和弦的内置默认候选；
3. 用户可以在当前转调状态重新选择目标和弦指法；
4. 本版本每个基础和弦只保存最后一次选择；在另一转调状态为同一基础和弦重新选择，会替换先前选择；
5. 恢复默认后重新使用原谱来源指法；没有来源指法时使用内置排序第一项。

### 5.7 保存、导出与删除

选择内置候选时，将其完整结构和核验记录复制到歌曲 `voicings`，再让匹配事件引用该 `voicingId`。因此结果不依赖未来指法库顺序，也能随谱包导出。

恢复默认时：

1. 清除本次选择写入的事件引用；
2. 删除已经没有事件引用、且由选择操作写入的冗余指法；
3. 不删除原谱来源指法或其他既有谱包指法。

## 6. 指法库来源与维护

### 6.1 主数据源

继续使用 `@tombatossals/chords-db` v0.6.0 作为多指法主库：

- 仓库：https://github.com/tombatossals/chords-db
- 许可证：MIT
- 当前项目基线：828 个和弦条目、3,283 个指法

本版本不因新增选择界面而整体替换主库。

### 6.2 补充与交叉校验来源

使用 ChordPro 6.101 标准吉他配置作为补充和交叉校验来源：

- 仓库：https://github.com/ChordPro/chordpro
- 许可证：Artistic License 2.0
- 标准吉他配置约 1,155 个唯一和弦名称，以每个名称一个指法为主

ChordPro 不替代现有多指法主库。本版本只合入其与现有库完全同形的 240 个位置索引至 `src/data/chordpro-common-voicing-order.json`，仅用于低把位候选并列时的排序；不复制 ChordPro 的完整指法位置，也不自动合并其余冲突或缺失形状。该派生索引保留固定版本、commit、许可证和定弦，并已更新 `THIRD_PARTY_NOTICES.md`。

### 6.3 数据进入仓库的门槛

1. 来源、版本、许可证和原始链接完整；
2. 定弦、品位、手指、横按和数组长度通过结构校验；
3. 重复形状被去重；
4. 支持解析的和弦后缀通过音高组成检查；
5. 常见和弦完成跨来源抽检；
6. 运行时不联网获取指法；
7. 许可不清楚或结构无法可靠转换的数据不进入正式库。

## 7. 制谱 Skill 字符对字符锚定

### 7.1 强制规则

PDF、截图和保留列布局文本必须以和弦根音字母的左边缘为标记，映射到歌词行中实际对齐的精确字素边界：

1. 只有根音字母本身对齐单词首字母时，才锚定到词首；
2. 根音落在词内字符时保留词内边界；
3. 根音落在空白列时保留该空白边界；
4. 对锚定有意义的行首和行尾空白不能提前裁剪；
5. 每个锚点写入后必须回到原始视觉来源逐个复核；
6. 无法直接判断时标记不确定，不能伪装为高置信。

运行时继续严格消费 `graphemeOffset`，不增加词首吸附逻辑。

### 7.2 Notion 回归样例

本版本保留以下强制回归：

```text
For I have seen the ending and there is no ascending rise
                                                     A Faug
```

- A → `rise` 的 `r`，`graphemeOffset: 53`；
- Faug → `rise` 的 `s`，`graphemeOffset: 55`；
- A → `ascending` 开头（43）或 Faug → `rise` 的 `r`（53）均为失败。

当前修正版 `output/notion-the-rare-occasions.chordsheet.json` 和 `.chordsheet` 包含 59 个歌词锚定和弦事件与 16 个纯和弦行事件。修正记录包括 17 个锚点调整、保留 5 行前导空格和 1 行尾随空格，并完成 59 个歌词和弦的逐项视觉复核，记录结果为 0 处不匹配。

## 8. 有谱么兼容导出

“复制到有谱么”必须生成结构化剪贴板内容，而不是普通歌词。用户粘贴到有谱么网页编辑器后，应能继续编辑，并完整保留段落顺序、逻辑换行、歌词与空格、当前显示的和弦名称、字符级和弦落点以及纯和弦行的事件顺序。

### 8.1 交互与结果

已打开谱面时，顶部导出区增加“复制到有谱么”。应用按当前显示调生成内容；成功后提示用户前往有谱么粘贴，剪贴板权限失败时提供可全选复制的只读文本框。按钮只表示已经复制，不表示已经上传、保存或发布。

“完整还原”指内容与锚点语义一致，不要求两个产品使用相同字体、间距、指法图或响应式布局。

### 8.2 范围与限制

导出器将段落、文本、和弦锚点和换行转换为有谱么样本中的 `HEADLINE`、`TEXT`、`CHORD_ANCHOR` 与 `LINE_BREAK`。字符映射必须沿用 ChordSheet 的精确字素位置，例如 A→`rise` 的 `r`（53）、Faug→`rise` 的 `s`（55），不得吸附到词首或清理承担对齐作用的空白。具体节点协议与转换算法由 `implementation-v0.2.0.md` 第 9 节定义。

样本协议不包含标题、歌手、Capo、节奏型、来源、`section.repeat` 或 `voicingId`。这些内容不会自动传递，具体指法由有谱么自己的指法库决定；应用必须在复制前说明影响。

### 8.3 兼容性验收

该功能依据用户在 2026-07-23 提供的实际剪贴板样本实现，不是有谱么官方 API。公开帮助页（https://yopu.co/help）没有说明剪贴板节点协议，因此本地结构测试只能用于排错，不能证明兼容。

发布前必须使用仓库已经保存的 The Cure 基准谱`output/the-cure-test-run/the-cure-olivia-rodrigo.character-anchor-test.chordsheet`，把它生成的内容粘贴到真实有谱么网页编辑器，逐项确认段落、换行、歌词、和弦名称和字符落点均无偏差，并记录验收日期和环境。不得用临时谱或简化夹具替代该项兼容性验收；协议变化导致失败时，不影响标准`.chordsheet`导出。

## 9. 用户流程

### 9.1 更换本曲 C 指法

1. 用户打开歌曲，在顶部和弦概览看到 C 指法图；
2. 点击指法图，选择器显示 4 个候选；
3. 用户查看开放弦、横按、把位和跨度标签；
4. 用户选择第二个候选并确认；
5. 概览与正文中全部基础符号为 C 的事件立即更新；
6. 页面自动保存，导出的 `.chordsheet` 保留该选择。

### 9.2 恢复默认

1. 用户再次打开 C 的选择器；
2. 点击“恢复默认指法”；
3. 有原谱来源指法时恢复原谱指法；
4. 否则恢复内置排序第一项；
5. 自动清理不再引用的用户选择副本。

### 9.3 转调后选择

1. 用户已为原调 C 选择指法；
2. 升半音后页面显示 C#，不能继续显示 C 的形状；
3. C# 使用其默认候选，用户可在当前状态重新选择；
4. 当前基础 C 只保留最后一次明确选择。

### 9.4 复制到有谱么

1. 用户把谱面调整到准备使用的调；
2. 点击“复制到有谱么”；
3. 应用列出不会随剪贴板传递的设置，并生成兼容内容；
4. 用户打开有谱么网页编辑器并粘贴；
5. 编辑器自动建立段落、歌词行和和弦锚点；
6. 用户逐段核对显示，随后自行保存或发布。

## 10. 验收标准

### 10.1 多指法功能

1. 导入已保存的 The Cure 基准谱后，标准定弦 C 只显示第 1、3、5 把的 3 个候选，第一项为开放 C 形；任一和弦去重后最多显示 4 个候选，默认内置候选的起始把位不高于第 5 把；
2. 选择任一候选后，本曲全部基础符号为 C 的事件同步更新；

## 11. 风险与控制

| 风险 | 控制 |
|---|---|
| 点击指法图与原有“展开全谱”行为冲突 | 全谱切换只保留明确按钮；指法图点击改为打开选择器 |
| 用户选择因指法库升级而错位 | 将完整选择复制进歌曲 `voicings`，不持久化内置数组下标 |
| 选中的 C 指法错误用于 C# | 解析时同时校验显示和弦、定弦与保存指法的 `chordSymbol` |
| 恢复默认误删来源指法 | 只清理选择操作创建且已无引用的指法 |
| “常用”被误解为流行度或高把位变体 | 说明没有使用频次统计；高于第 5 把的内置位置不进入默认候选，ChordPro 只作低把位并列排序 |
| 第二数据源引入许可混乱 | 固定版本、保留来源、更新第三方声明；未审清前不合入 |
| JSON 合法但视觉锚定错误 | Skill 强制逐和弦回看来源，并保留 Notion 精确偏移回归 |
| 空白规范化改变锚点 | 在字符映射完成前保留有对齐意义的首尾空白 |
| 有谱么格式变化或本地测试无法反映真实显示 | 隔离转换器并强制执行真实编辑器验收；失败不影响标准谱包 |
| 用户误以为自选指法、Capo 或元数据会被带入 | 导出当前显示和弦名称，并在复制前列出未传递内容 |
| 复制内容包含未支持节点或语义 | 导出前预检并列出降级项，不静默丢失 |

## 12. 版本完成定义

只有同时满足以下开发完成与交付准备条件，v0.2.0 才能从 `draft` / `planning` 转为发布候选：

1. 第 10 节中可由开发侧执行的验证全部完成，待项目负责人确认的验收项在 Release 中明确标记；
2. 多指法选择、恢复默认、转调与谱包往返均有自动化覆盖；
3. 指法库审计记录与第三方声明完成；
4. Skill 规则、Schema 副本和可下载 ZIP 同步；
5. Notion 锚定回归通过；
6. 有谱么结构化转换、本地往返和真实网页编辑器粘贴验收通过；
7. 创建状态为 `release-candidate` 的 Release 文档记录实际结果，并与版本交付同步；
8. `package.json` 版本更新为 `0.2.0`。

项目负责人验收期间，Release持续记录偏差与处理结果。验收通过后才能定稿为`released`；验收未通过时回到开发，并更新同一份Release候选。
