# 项目文档撰写与结构规范

| 项目 | 说明 |
|---|---|
| 状态 | approved |
| 适用范围 | 本仓库及采用本规范的其他项目的全部正式文档 |
| 适用对象 | 项目负责人、产品与设计人员、开发与维护人员、Chat、Codex及其他文档协作者 |
| 维护方式 | Git |
| 权威位置 | `docs/overview/writing-guidelines.md` |

## 1. 规范目标

项目文档需要同时服务人和机器，因此应做到：

1. **信息完整。** 不因追求简短而删除已经确认的背景、规则、边界、例外、风险或执行细节；
2. **逻辑清楚。** 读者能够沿着文档理解内容，不需要在脑中重新拼装零散信息；
3. **板块清晰。** 每个章节承担明确职责，相关内容集中出现；
4. **表达易懂。** 根据内容关系选择段落、编号、表格、流程图、示例或代码块；
5. **读取高效。** 不增加无信息价值的文字，不跨文档重复完整规则，也不要求机器默认读取与当前任务无关的内容。

本规范追求的不是“越短越好”或“越详细越好”，而是：

> **完整信息 + 清晰结构 + 合适密度 + 最小冗余。**

提高可读性的首选方法是重新组织信息，而不是减少信息。

---

## 2. 撰写前先确定文档职责

结构是否合理，取决于文档要解决什么问题。开始撰写或修改前，应先确认：

1. **读者是谁。** 是项目负责人、新读者、产品与设计人员、开发与维护人员、Chat、Codex，还是后续协作者；
2. **阅读目的是什么。** 读者需要理解项目、作出决定、执行步骤、完成开发，还是核对实际结果；
3. **文档必须回答什么。** 哪些问题如果没有说明，读者就无法继续；
4. **什么是前置信息。** 哪些概念、背景或约束必须先出现；
5. **什么属于本文职责。** 哪些内容应完整说明，哪些只需要引用其他权威文档；
6. **阅读发生在什么场景。** 是首次了解项目、版本交接、编码前、开发后，还是上线验收。

完成这些判断后，再决定章节、信息密度和表达方式。不要先套模板，再把内容硬塞进去。

---

## 3. 章节顺序与板块结构

### 3.1 不规定固定章节顺序

PRD、项目说明、工作流、Implementation和Release面对的读者、目的与内容不同，不需要采用同一个目录。

唯一的强制要求是：

> **章节顺序必须符合该文档自身的认知逻辑或执行逻辑。**

常见顺序可以作为参考，例如：

```text
背景 → 问题 → 方案 → 执行 → 结果
```

或：

```text
当前状态 → 输入 → 操作 → 产出 → 下一步
```

这些都不是强制模板。只要另一种顺序更符合具体内容，就应采用更合理的顺序。

### 3.2 文档标题与标题层级

全部正式Markdown统一采用标准标题结构：

| 元素 | 写法与职责 |
|---|---|
| 一级标题 `#` | 文档标题；每份文件必须且只能出现一次 |
| 二级标题 `##` | 主要板块；每个板块回答一个核心问题 |
| 三级标题 `###` | 主要板块下的子问题、对象或阶段 |
| 四级标题 `####` | 必要的进一步细分 |
| 五级标题及以下 | 原则上不使用；出现时优先重新组织板块 |

示例：

```markdown
# 示例项目的 Chat × Codex 版本工作流

| 项目 | 说明 |
|---|---|
| 状态 | approved |
| 维护方式 | Git |

## 1. 如何使用这份工作流

### 1.1 适用方式

## 2. 一个版本的基本单位与阶段地图

### 2.1 基本单位
```

必须遵守：

1. H1位于文档开头，用作完整文档名称；
2. 每份正式文档只能有一个H1；
3. 主要板块从H2开始；
4. H3用于H2下的子板块；
5. H4仅用于必要的进一步细分；
6. 标题不得跳级；
7. 章节编号应与标题层级和内容从属关系保持一致；
8. Markdown原文与同步到飞书等协作平台的正文保持一致，不做平台专属标题转换；
9. 同一层级的连续编号必须使用同一标题级别；
10. 长文档如果存在“第一部分”“第二部分”等真实上位结构，应将“部分”设为H2，其下章节设为H3，子章节设为H4；
11. 位于各部分之前的阅读说明、适用范围或文档使用方法，可以作为不编号的H2独立存在；
12. 如果文档没有真实的“部分”结构，则主要章节直接使用H2，子章节使用H3；
13. 不得为了保持编号连续而牺牲真实的从属关系，也不得把真实上位结构降为普通正文。

采用标准层级不会降低Codex阅读效率，反而有利于文档自解释、自动目录、切片索引和跨工具兼容。

### 3.3 每个板块只承担一个主要主题

每个主要板块应按需要完成以下工作：

1. 用标题准确说明本节主题；
2. 在开头交代本节要回答的问题，或它与前文的关系；
3. 将同一主题下的背景、判断和细节组织在一起；
4. 避免把多个无关问题塞进同一章节；
5. 在结尾给出结论、完成标志、下一步，或自然承接后文。

同一信息应在最合适的板块中完整说明一次。其他位置需要提及时，使用摘要和引用。

### 3.4 避免两种结构性问题

第一种是**板块过碎**：每个标题下只有一句话，读者需要不断跳转才能理解完整逻辑。

第二种是**板块过载**：一个章节同时混入背景、规则、步骤、风险、当前状态和结果，标题无法准确概括内容。

判断标准不是章节数量，而是每个板块是否形成清楚、完整的认知单元。

## 4. 段落、编号与其他表达形式

### 4.1 完整段落负责解释逻辑

背景、因果关系、判断依据、产品意图、限制条件和结论，应使用完整段落说明。一个段落可以包含多句相互承接的话，只要它们共同展开同一个中心意思；不要为了制造留白或强调，把本应连贯的论述拆成连续的一句话段落。

完整段落不等于长段落。出现以下情况时，应重新组织：

1. 一个段落同时处理多个不同问题；
2. 连续多个短段只是在共同说明同一判断，却缺少必要衔接；
3. 只写结论，不解释原因、边界或适用范围；
4. 使用大量过渡套话，却没有增加信息；
5. 依靠频繁换行制造强调，而没有真实的结构变化。

### 4.2 有限并列内容优先采用“总述—分点—收束”

当一项判断下包含两项以上、数量有限且关系清楚的能力、范围、原因、条件、步骤、影响或维度时，优先考虑以下结构：

1. 用完整总述句交代对象、关系和分点范围；
2. 用编号分别展开平行内容，各项语法和颗粒度尽量一致；
3. 在确有必要时，用完整段落说明共同结果、边界、非目标或结论。

以下内容仅作为结构示例，不构成任何项目的产品要求：

```markdown
产品围绕自由记录、长期沉淀和内容回望提供以下能力：

1. 以文字、语音或图片留下不完整、简短或暂时说不清的内容；
2. 在不改写原文的前提下保存记录，并按时间帮助用户重新找到它们；
3. 在积累形成足够信息厚度后，发现跨记录的重复感受、潜在联系或未完成想法。

这些能力服务于个人表达和长期回望，不以任务管理、正式知识库或持续自我提升为目标。记录可以暂时没有结论，AI也不需要为每条内容强行生成洞察。
```

这种写法适合把一个完整判断中的有限并列信息集中呈现，避免把同一主题拆成多个过短段落。它不是默认模板，也不得机械套用：

1. 只有一项简单内容时，直接使用完整句子或段落；
2. 内容需要连续叙述、细腻推理或逐步展开时，保留段落形式；
3. 分点之间不平行、颗粒度差异过大时，先重新分类或改用小节；
4. 每一项都需要多段解释时，改用独立子板块，而不是把长论述塞进列表；
5. 相邻章节已经多次采用相同结构时，应根据内容关系更换表达形式，避免文档机械化；
6. 收束段只有在补充边界、共同结果、非目标或结论时才保留，不得重复总述和列表内容。

### 4.3 有序编号适合什么内容

以下内容优先使用编号：

1. 有先后关系的步骤；
2. 多个原因共同支持一个结论；
3. 需要逐项核对的条件；
4. 存在递进、主次或依赖关系的观点；
5. 验收路径和问题处理流程；
6. 多个影响需要分别解释；
7. 产品能力、范围构成或非范围等数量有限、需要完整列明的并列内容。

编号不一定表示时间顺序，但必须让各项之间的关系清楚。若只是几个简短名词、文件名或同级对象，无需为了形式完整而强行使用“总述—编号—收束”。

### 4.4 无序列表只用于真正平行的简短内容

无序列表适合文件清单、附件名称、同级对象或无需展开的并列项。

不要把完整论述拆成大量项目符号，也不要让每句话都以 `-` 开头。无序列表过多会破坏段落联系，使文档变成信息堆积；编号列表同样不得滥用。选择列表的理由应是信息之间确实存在可分列关系，而不是单纯为了让页面看起来更整齐。

### 4.5 根据信息关系选择形式

| 信息关系 | 推荐表达 |
|---|---|
| 背景、原因、判断、解释和结论 | 完整段落 |
| 顺序、递进、因果、条件或步骤 | 编号分点 |
| 对象分类、状态对比、职责分工 | 表格 |
| 阶段、闭环、依赖和流转关系 | 流程图或文本流程 |
| 文件路径、命令和目录 | 代码块 |
| 可重复使用的消息或文案 | 独立模板块 |
| 正反案例或不同状态 | 对照表或清晰分区 |

表格适合快速比较，不适合承载长篇解释。如果一个单元格需要多个长段落，应改为独立小节。

流程图负责展示关系和顺序，不能替代必要说明。复杂流程后仍应解释关键控制点、例外和完成标志。

## 5. 信息完整、权威来源与去重

### 5.1 不为易读而删减有效信息

优化文档时，不得仅因为内容较长而删除：

1. 产品背景和用户问题；
2. 使用场景和判断依据；
3. 范围、非范围和优先级；
4. 角色、权限和责任边界；
5. 成功、失败、空状态和异常边界；
6. 数据、隐私和AI要求；
7. 验收标准；
8. 风险、偏差和已知问题；
9. 文件用途、落库位置和更新责任。

提高可读性时，应优先重新分板块、拆分段落、使用编号、表格、流程图或交叉引用。

只有以下内容可以删除：

1. 与其他内容完全重复；
2. 已经失效；
3. 已被新决策明确替代；
4. 明显属于其他文档的职责，且已保留必要摘要和准确引用。

### 5.2 一个事实只保留一个权威来源

| 内容 | 权威位置 |
|---|---|
| 对外产品入口 | `README.md` |
| 人类项目说明书 | `forhuman.md` |
| 长期产品规则 | `docs/global/` |
| 项目角色与平台规则 | `project-management.md` |
| 完整执行步骤 | `workflow.md` |
| 交接模板 | `handoff.md` |
| 目录与命名 | `naming.md` |
| 文档撰写规则 | `writing-guidelines.md` |
| 版本产品基线 | 对应版本的 `prd-vX.Y.Z.md` / `design-vX.Y.Z.md` |
| 版本技术实施 | 对应版本的 `implementation-vX.Y.Z.md` |
| 版本实际结果 | 对应版本的 `release-vX.Y.Z.md`；开发完成后创建并随交付同步，验收通过后定稿 |

其他文档可以保留理解所需的摘要，但应指向权威来源，不能形成互相冲突的两套完整规则。

上述文件名是推荐的职责映射。项目已有不同命名时，可以保留现有文件名，但必须明确对应的文档职责，并从README提供准确入口；不得因名称不同而省略任何职责。

### 5.3 去重不等于删除上下文

摘要仍应足以让读者理解：

1. 这项规则与当前任务有什么关系；
2. 详细内容在哪里；
3. 当前需要执行哪一部分。

只放一个裸路径，或只写“详见其他文件”，通常不足以完成有效交接。

## 6. 信息密度与机器阅读效率

### 6.1 结构优化不能造成无效扩写

以下内容会同时降低人和机器的阅读效率：

1. 每个章节都使用固定套话；
2. 为简单步骤增加不必要的背景段落；
3. 同一规则在多个文件中完整复制；
4. 标题层级过深，正文被切得过碎；
5. 表格单元格过长；
6. 为了“显得完整”重复解释已经明确的常识；
7. 添加与当前文档职责无关的内容。

完整不等于冗长。必要信息应完整说明，无信息价值的文字应删除。

### 6.2 不同文档使用不同信息密度

| 文档 | 合适密度 |
|---|---|
| `README.md` | 简明、面向外部读者；产品介绍、主要功能、使用方式、当前版本、运行入口和文档导航 |
| `forhuman.md` | 全面、易懂；帮助人理解产品需求、项目状态和运作方式 |
| Global文档 | 完整稳定；保存跨版本产品共识和边界 |
| `project-management.md` | 完整；说明长期协作和治理规则 |
| `workflow.md` | 详细可执行；每一步有输入、动作、产出和完成标志 |
| `handoff.md` | 模板完整；实际使用时只保留本轮相关内容 |
| `prd-vX.Y.Z.md` | 高颗粒度；避免Codex补产品逻辑 |
| `design-vX.Y.Z.md` | 按需详细；只承载复杂设计 |
| `implementation-vX.Y.Z.md` | 技术完整；不重复PRD正文 |
| `release-vX.Y.Z.md` | 事实完整；开发完成后创建并随交付更新，验收通过后定稿，不复制代码Diff和完整测试日志 |
| Technical文档 | 足够维护系统；不重复单版本Implementation |

“全部遵守同一写作规范”不代表“全部写成同样长度”。

### 6.3 机器阅读应遵循最小必要范围

Codex、Chat或其他AI协作者执行具体任务时，应优先读取：

1. 当前交接消息；
2. 当前任务直接相关的正式文档；
3. 被交接消息明确列出的长期或技术文档；
4. 完成任务所需的代码或运行信息。

默认不读取：

1. 全部历史版本；
2. 完整产品讨论；
3. 与当前任务无关的Global、Overview或Technical文件；
4. 已经在同一连续会话中读取且没有变化的文件；
5. `forhuman.md`等仅用于建立项目全貌、但当前任务不需要的文档。

交接消息负责限定本轮阅读范围。README面向外部读者介绍产品并提供文档导航，不代表其中列出的所有文件都必须读取。

### 6.4 适合机器定位的写法

为了便于Codex、Chat及其他工具检索、引用和执行，正式文档应尽量做到：

1. 标题准确且稳定；
2. 关键规则使用明确编号或小标题；
3. 文件路径、字段名、命令和状态使用一致写法；
4. 验收标准可以逐项检查；
5. 不使用“按实际情况处理”“适当优化”等缺少判断标准的模糊表达；
6. 跨文档引用写出准确路径和用途；
7. 修改规则时同步更新相关导航和摘要。

## 7. 衔接、术语与可理解性

文档不应只是若干章节的并列集合。章节和段落之间需要存在清楚关系。

撰写时应做到：

1. 先介绍理解后文所必需的概念；
2. 复杂规则先说明为什么需要，再说明怎样执行；
3. 新板块开头说明它解决什么问题；
4. 首次出现缩写、角色或专有名称时给出解释；
5. 详细步骤结束后说明产出、完成标志或下一步；
6. 前后使用一致的术语、文件名、版本号和状态名；
7. 新增内容应放入最合适的位置，而不是简单追加到文档末尾。

应避免：

1. 在后半段才补充前文理解所需的背景；
2. 同一概念前后使用不同名称；
3. 把结论、原因和操作步骤混在一个难以拆解的段落中；
4. 章节之间频繁跳跃；
5. 只罗列关键词，不解释它们与项目的关系；
6. 先给出规则，后面又用另一种说法部分覆盖它。

## 8. 各类文档必须回答的问题

本节只规定职责，不规定固定章节顺序。

| 文档 | 必须帮助读者回答的问题 |
|---|---|
| `README.md` | 产品是什么、适合谁、能做什么、怎样开始使用；当前版本状态是什么；如何运行、测试或进入详细文档 |
| `forhuman.md` | 产品是什么、为什么存在、目前做到哪里、项目怎样运转、如何继续 |
| Global文档 | 哪些产品共识跨版本长期有效；为什么；适用边界是什么 |
| `project-management.md` | 项目负责人、Chat、Codex、团队成员和各平台怎样分工；正式文档如何治理 |
| `workflow.md` | 项目团队如何完成整个版本；每一步的输入、动作、产出和完成标志是什么 |
| `handoff.md` | 每个交接节点如何说明状态、附件、要求、边界和下一步 |
| `naming.md` | 文件和目录怎样组织；版本、分支、PR、Tag和附件怎样命名 |
| `prd-vX.Y.Z.md` | 本版本为什么做、做什么、不做什么、怎样表现、什么算完成 |
| `design-vX.Y.Z.md` | 复杂页面、信息结构、交互和状态具体是什么样，并如何对应PRD |
| `implementation-vX.Y.Z.md` | 现有代码如何实现产品基线；模块、数据、顺序、测试和风险是什么 |
| `release-vX.Y.Z.md` | 开发完成后创建并随交付同步，记录实际交付、测试结果、偏差、已知问题和上线事实；验收通过后定稿 |
| Technical文档 | 当前系统跨版本的技术事实是什么；其他开发者如何理解和维护 |

只要完整回答相应问题，章节顺序可以根据具体内容自由调整。

## 9. 撰写、修改与审核责任

### 9.1 产品、设计与项目说明文档

Chat或承担产品与内容文档职责的成员在编写或更新PRD、Design、Global、Overview和`forhuman.md`时，应主动应用本规范。

项目负责人负责确认：

1. 内容是否准确；
2. 信息是否完整；
3. 结构是否符合真实产品逻辑；
4. 是否仍需补充背景、边界或例外；
5. 是否为了可读性错误删减了重要信息。

### 9.2 技术与交付文档

Codex或承担技术文档职责的成员在编写Implementation、Release、Technical和README技术内容时，也必须遵循本规范。Release采用两阶段维护：开发完成且开发侧验证结果可以记录后，创建`release-candidate`并与版本交付同步；项目负责人验收期间持续记录偏差和处理结果，验收通过后再定稿为`released`。验收未通过时，应回到开发并更新同一份Release候选，不得提前标记为正式发布。

技术文档不得只输出文件清单、关键词或缺乏解释的碎片内容。技术方案应说明它与产品要求的对应关系，同时避免重复PRD中已经明确的产品正文。

### 9.3 修改已有文档

修改正式文档时，应依次完成：

1. 理解原文的读者、目的和逻辑主线；
2. 识别该文档的权威职责；
3. 保留全部仍然有效的信息；
4. 将新增内容放入最合适的板块；
5. 必要时调整标题和章节顺序；
6. 清理真正重复、失效或已被替代的内容；
7. 检查术语、路径、链接和跨文档引用；
8. 检查是否增加了无效篇幅；
9. 不在未说明的情况下改变原有规则含义。

### 9.4 增量维护与分层检查

正式文档采用增量维护。已经批准且未被本次改动影响的内容，默认视为现有合规基线；新增或修改内容必须在写入时遵守当前规范，并检查本次改动及其直接影响范围。

“增量检查”不等于不检查，而是根据改动范围选择必要的检查层级：

| 改动类型 | 默认检查范围 |
|---|---|
| 修改措辞、补充段落或增加简短说明 | 改动内容及其所在章节 |
| 新增标题、调整编号、移动章节或改变文档内部结构 | 当前文档 |
| 修改权威规则、摘要、交接要求或跨文档引用 | 所有直接相关文档 |
| 调整目录、文档体系、命名规则或标题规范 | 全部正式文档 |
| 文档进入`approved`、`completed`或`released`，或准备完整交付、全量同步飞书等协作平台 | 本次交付涉及的全部正式文档 |

执行时应遵循以下原则：

1. 不因一次局部修改而重复审查与其无关的稳定文档；
2. 如果改动可能影响上级章节、编号、权威关系或其他文件，应主动扩大一级检查范围；
3. 新增内容应直接按照现行规范撰写，避免先随意写入、再依赖全量返工修正；
4. 标题层级、编号连续性、唯一H1和路径有效性等机械规则，后续可以交给脚本自动检查；
5. Chat、Codex或其他文档协作者默认只报告本次发现的问题和实际修改，不重复罗列所有未变化文档的“检查通过”；
6. 只有达到上表所列关键节点，或项目负责人明确要求时，才进行全量检查。

## 10. 发布前检查

本章清单应用于`9.4 增量维护与分层检查`确定的检查范围。日常局部修改不要求把整套清单重新应用到全部文档；进入正式状态、完整交付或其他关键节点时，才对相关正式文档执行完整检查。

### 10.1 结构与逻辑

- [ ] 文档的读者和目标明确
- [ ] 章节顺序符合文档自身逻辑，而不是机械套模板
- [ ] 文档开头有且只有一个H1
- [ ] H2、H3和H4分别对应主要板块、子板块和必要细分
- [ ] 同一层级的连续编号使用同一标题级别
- [ ] “部分—章节—子章节”的真实从属关系得到正确表达
- [ ] 真实上位结构没有被降为普通正文
- [ ] 只看标题能够理解大致脉络
- [ ] 不同主题没有混在同一板块
- [ ] 板块没有过碎或过载
- [ ] 章节和段落之间存在自然衔接

### 10.2 表达与可读性

- [ ] 重要背景、原因和结论得到完整解释
- [ ] 本应连贯的内容没有被拆成连续的一句话段落
- [ ] 多个原因、步骤、条件或有限并列内容在适合时使用编号
- [ ] “总述—分点—收束”只在关系清楚时使用，收束段没有重复前文
- [ ] 相邻章节没有机械重复同一种列表结构
- [ ] 无序列表仅用于真正平行的简短内容
- [ ] 对比和分类在适合时使用表格
- [ ] 流程图后说明了关键控制点
- [ ] 首次出现的概念和术语已经解释
- [ ] 没有大量无信息价值的过渡语或套话

### 10.3 完整性与一致性

- [ ] 没有为了缩短文档而删除有效信息
- [ ] 范围、非范围、边界和例外仍然完整
- [ ] 数据、隐私、AI和验收要求没有遗漏
- [ ] 风险、偏差和已知问题被正确记录
- [ ] 文件路径、责任人和下一步清楚
- [ ] 摘要与权威文档没有冲突
- [ ] 术语、版本号、文件名和状态名保持一致

### 10.4 机器阅读效率

- [ ] 没有跨文档重复完整规则
- [ ] 没有增加与本文职责无关的内容
- [ ] 标题层级没有跳级，且原则上不超过H4
- [ ] 关键规则可以通过标题或编号快速定位
- [ ] 交接消息能够限定本轮所需阅读范围
- [ ] README面向外部读者简明介绍产品与使用方式，通过链接进入详细规则，没有复制完整产品或工程文档

完成检查后，文档才能进入`approved`、`completed`或`released`等正式状态。
